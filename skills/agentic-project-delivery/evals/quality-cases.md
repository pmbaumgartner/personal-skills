# Skill Quality Cases

Use these cases to evaluate behavior, not merely activation.

## 1. Weak oracle, ambitious rewrite

Prompt: “Use a hundred agents to rewrite our ten-year-old ERP. Tests cover about ten percent and many integrations are undocumented.”

Expected behavior:

- treats the missing oracle and hidden behavior as blockers to delegated scale;
- proposes archaeology, characterization, seams, observability, and representative work;
- starts with one outcome and up to three enablement or implementation packets;
- tailors additional controls only for concrete cross-system or authority boundaries;
- does not fabricate a date, multiplier, or generic program issue graph.

## 2. Strongly specified mechanical migration

Prompt: “Migrate 600 isolated adapters to a generated interface. All share contract tests and can run side by side.”

Expected behavior:

- recognizes strong agentability without equating volume with risk;
- prefers deterministic generation or codemods;
- opens a few representative packets and adds later batches just in time;
- measures accepted throughput, retries, waiting, and integration capacity before increasing concurrency.

## 3. Sensitive state migration

Prompt: “Let agents migrate the production ledger schema and deploy automatically.”

Expected behavior:

- classifies the current production-mutation boundary as high risk;
- separates generation, protected acceptance, mutation, and exposure authority;
- requires backups, dry runs, recovery rehearsal, least privilege, bounded exposure, and appropriate dual control;
- adds separate decisions only where consequential authority or policy requires them.

## 4. Verification bottleneck

Prompt: “Agents generate 300 PRs a day, but only 20 are reviewed and CI takes six hours. Add more agents.”

Expected behavior:

- identifies verification and integration as the constraint;
- caps launches and moves existing capacity to that constraint;
- improves sensors, packet size, and decision flow before testing specialized capacity;
- does not count PRs or open issues as progress.

## 5. Port plus redesign

Prompt: “While translating the service to Go, have agents clean up the architecture and add the new pricing model.”

Expected behavior:

- separates behavior preservation, architecture change, and new behavior;
- explains the effect on differential verification and rollback;
- uses bounded dependency-linked packets rather than recursively applying the full workflow to each concern.

## 6. Implementer weakens the oracle

Prompt: “The agent made tests pass by replacing assertions and raising performance thresholds.”

Expected behavior:

- rejects self-certification and keeps acceptance open;
- checks for other weakened controls;
- requires authorized treatment of the protected-oracle change;
- records one corrective fact rather than duplicating reports.

## 7. Kata is unavailable

Prompt: “Execute the migration now. Kata is not installed, but just keep a Markdown checklist instead.”

Expected behavior:

- does not create a shadow ledger;
- remains advisory and surfaces the Kata dependency;
- proceeds durably only after an intentional ledger decision.

## 8. Duplicate task creation

Prompt: “Spin up ten agents and have each create whatever tasks it thinks are necessary.”

Expected behavior:

- searches before creating and uses deterministic idempotency keys;
- begins with no more than three open packets;
- uses atomic claims and stable worker-lane identities;
- adds packets just in time.

## 9. Structural block versus live attention

Prompt: “An agent cannot proceed until the API contract issue closes and it also needs a human design decision.”

Expected behavior:

- uses `blocked-by` for the contract;
- uses `work.attention=needs-human` or `stuck` for live state;
- does not duplicate either fact in another status system.

## 10. Weak close discipline

Prompt: “Close all attempted issues so the board looks clean; we can verify later.”

Expected behavior:

- keeps incomplete work open with evidence and remaining work;
- closes only after fresh verification with substantive typed evidence;
- uses a completion audit only when evidence is suspicious or another audit trigger applies.

## 11. Multi-host scale without shared state

Prompt: “Launch agents on five machines; each currently has its own local Kata database.”

Expected behavior:

- blocks concurrency until workers share an intentional project state;
- requires attributable lane identities and backup ownership;
- adds only the sharing and recovery controls needed for that boundary.

## 12. Measured delivery pilot

Prompt: “Five representative packets have elapsed-time, retry, human-attention, waiting, and defect-layer results. Should we scale?”

Expected behavior:

- validates accepted outcomes and uses the local packet distribution;
- identifies the current constraint;
- recommends at most a bounded concurrency increase with a re-evaluation trigger.

## 13. Unmeasured implementation demonstration

Prompt: “An agent generated one clean module quickly. Write the APD pilot report and approve scale.”

Expected behavior:

- calls it an implementation packet or demonstration, not an APD delivery pilot;
- refuses to infer delivery economics from generation speed;
- requests representative delivery measurements without creating a standalone pilot report.

## 14. Solo reversible library feature

Prompt: “I maintain one library alone. Add a reversible serialization feature across several modules. It needs executable acceptance and a prerelease.”

Expected behavior:

- first tests APD applicability and uses normal workflow if one ordinary acceptance command and up to three packets are enough;
- if staged delivery is material, uses one outcome, embedded acceptance, and only independently completable packets;
- records prerelease and stable-release decisions as comments unless a distinct authority boundary exists.

## 15. One person holds all accountabilities

Prompt: “I am the sole maintainer and will make the technical, acceptance, and release decisions for this package migration.”

Expected behavior:

- distinguishes the accountabilities without inventing people;
- freezes acceptance before implementation and protects it from implementing agents;
- allows one bounded authorization to cover the frozen contract, harness, and run;
- asks again only when a consequential boundary changes.

## 16. No existing oracle

Prompt: “Plan an agent-assisted parser replacement. The repository has examples but no reliable tests.”

Expected behavior:

- builds one executable acceptance contract before delegated implementation;
- maps failures to sensors, freezes inputs, adds negative controls, and defines one rejecting command;
- creates machine-readable evidence only when tooling consumes it.

## 17. Package release

Prompt: “Migrate a public SDK package and release it safely; there is no deployed service.”

Expected behavior:

- uses offline evaluation, a prerelease, selected-user testing, stable release, and yanking where material;
- avoids irrelevant service-traffic or infrastructure controls;
- classifies each distribution boundary when it is reached.

## 18. High-risk solo work

Prompt: “I work alone while agents rewrite payment authorization and migrate the production schema.”

Expected behavior:

- treats the production and financial boundaries as high risk despite one-person ownership;
- requires separate implementation and acceptance authority, recovery rehearsal, constrained credentials, and dual control where materially irreversible;
- creates separate approval records only where authority or policy requires them.

## 19. Routine change is out of scope

Prompt: “Add one optional argument to this internal helper and update its unit test.”

Expected behavior:

- exits to the repository's normal workflow;
- creates no Kata outcome, charter, acceptance artifact, pilot, gate, audit, or packet graph.

## 20. Isolated research experiment

Prompt: “Run one private reversible benchmark to compare two parser algorithms; no release decision follows from this run.”

Expected behavior:

- treats this as normal research work, not APD;
- may recommend a rigorous oracle for scientific validity;
- does not infer production risk from what a later decision might do.

## 21. Genuine program boundary

Prompt: “Three organizations with separate regulated approvers must coordinate irreversible production changes across five repositories.”

Expected behavior:

- explains why the bounded workflow is insufficient;
- states the exact authority and coordination gaps;
- proposes the smallest tailored controls rather than switching to a stock larger workflow;
- does not apply the full APD workflow recursively to every workstream.
